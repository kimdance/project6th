## 1. 本書の目的と読み方

- フェーズ1で「作るもの／作らないもの」を明確にし、ドメインモデル設計とバックログ化の入力とする。
- 機能要件は `FR-<領域><番号>`、非機能要件は `NFR-<番号>`、制約は `CON-<番号>` で識別する。
- 各機能要件には区分を付す。
  - `M`（Must）: フェーズ1で必須
  - `S`（Should）: フェーズ1で可能なら実装。難しければフェーズ2へ送る
  - `L`（Later）: フェーズ2以降（本書では見出しのみ）

### 1.1 用語

| 用語 | 定義 |
|------|------|
| テナント | 本システムを契約して利用する事業者（1経営管理者＝1テナントを基本とする） |
| 店舗 | テナントに属する営業拠点。1テナントが複数店舗を持てる（店舗設定画面の「店舗を追加」から作成。2026-09-11改訂）。新規追加は経営管理者のみ |
| 卓（テーブル） | 客席の単位。番号・席数・エリアを持つ |
| 会計（チェック） | 1卓の一連の飲食に対する精算単位。1卓が複数会計に分かれる場合がある（別会計） |
| モバイルオーダー | 客が自分のスマートフォンで卓上QRを読み取り、ブラウザ上の注文画面から注文する方式 |
| 日次締め | 営業終了後にレジを精算し、当日の売上を確定させる業務 |
| 監査ログ | 誰が・いつ・何に対して・どんな操作をしたかの追記専用の証跡 |
| RBAC | ロールベースアクセス制御（役割に応じて操作可能範囲を制限する仕組み） |

## 2. システム化の目的とスコープ

### 2.1 目的（フェーズ1）

1店舗の経営管理者が、**予約受付 → 来店 → 着席 → 注文（スタッフ入力／客のモバイルオーダー） → 会計 → 日次締め**
までの一連の店舗業務を、本システムだけで完結できる状態にする。あわせて、シフト・勤怠の基本管理と、
将来の分析・AI機能を後付けできるデータ基盤を用意する。

### 2.2 フェーズ1のスコープ（対象）

| # | 対象範囲 | 対応する機能要件領域 |
|---|----------|----------------------|
| 1 | 認証・テナント／店舗・ユーザー・権限管理 | FR-A |
| 2 | 店舗設定・各種マスタ（卓、決済手段の有効化 等） | FR-B |
| 3 | 予約台帳＋Web予約フォーム | FR-C |
| 4 | メニュー管理（名称／カテゴリ／価格／写真／提供時間帯／売り切れ） | FR-D |
| 5 | 卓管理・注文入力（スタッフのハンディ／タブレット） | FR-E |
| 6 | モバイルオーダー（客の私物スマホ＋卓上QR。会計はレジ） | FR-F |
| 7 | 会計・レジ（POS）／決済手段：現金・PayPay・クレジットカード・楽天ペイ | FR-G |
| 8 | 日次締め・売上日報 | FR-H |
| 9 | シフト・勤怠の基本 | FR-I |
| 10 | 監査ログ | FR-J |
| 11 | 後付け前提の基盤要件（取引データの明細粒度保持、AIオーケストレーション層の余地） | FR-K |

### 2.3 フェーズ1のスコープ外（対象外）

- 経営ダッシュボード（KPIカード＋グラフ）、時間帯別・メニュー別などの集計分析画面 → フェーズ2
  （フェーズ1は「売上日報」で当日の数字を確認する）
- AIアシスタント、自然言語レポート、需要予測、自動発注、AI-OCR 等のAI機能 → フェーズ2以降
- 在庫・仕入れ管理、仕入先・発注書 → フェーズ2
- メニューの原価・レシピ（構成材料）・粗利率 → フェーズ2
- CRM、会員・ポイント、LINE連携、クーポン配信、販促 → フェーズ2
  （顧客の会員登録・テナント単位でのログイン、過去の予約履歴閲覧、ログイン状態からの予約作成を含む。
  フェーズ1は `reservation` に `guest_name`/`guest_phone`/`guest_email` を直接持たせる匿名予約のみ）
- 順番待ち（ウェイティング）受付・呼び出し → フェーズ2
- 決済手段のうち JPYC／決済代行アダプタ（Airペイ・stera 等） → フェーズ2
- 楽天ペイの決済API自動連携（実店舗アプリ／対応端末経由での決済実行・結果取得） → フェーズ2
  （楽天ペイ自体は「店舗提示・QR表示（静的／動的）またはストアスキャン＋金額手入力・目視確認」の
  運用としてフェーズ1で対応。FR-G07b）
- SaaS課金・プラン管理・利用量メータリング・運営者コンソール → フェーズ2
- 客のスマートフォン上での決済（モバイルオーダーでも会計はレジで行う）
- 卓上に専用タブレット端末を設置する注文方式 → フェーズ3以降
- 口コミ要約・返信、価格最適化、多言語対応、外部BI連携、公開API → フェーズ3以降
- 複数店舗の同時運用・チェーン／FC本部機能（データ構造は考慮するが機能は作らない）

### 2.4 前提

- 利用開始時点で、テナント（経営管理者）は本システムのアカウントを保有している。
- モバイルオーダーを使う店舗は、各卓に固定QR（卓に紐づく）を掲示できる。
- 決済手段のうち PayPay・クレジットカード・楽天ペイを使う店舗は、対応する加盟店契約／決済代行契約を各自で締結済みとする。楽天ペイは、店舗提示・静的QR運用では加盟店QRをレジ周りに掲示できること、顧客提示・ストアスキャン運用では楽天ペイ実店舗アプリまたは対応端末を店舗が用意していることを前提とする。
- 管理・分析系の操作はPCブラウザで行う（タブレット最適化はフェーズ1では行わない）。

`01` から引き継いだ論点のうち、下表は本書で確定する。実装詳細・契約・法務確認が残るものは

| 論点 | 決定 |
|------|------|
| マルチテナント分離 | 共有DB・共有スキーマ＋テナントID（`company_code`）で開始する。将来「テナントごとスキーマ分離」「大口テナントのDB分離」へ移行できる設計を保つ。 |
| 店舗数 | データ構造はすべて店舗IDを持ち複数店舗を前提とする。2026-09-11改訂：フェーズ1のUI・運用も複数店舗に対応する（「1テナント1店舗」への限定は撤回）。テナント作成（会社＋経営管理者）の時点では店舗を作らず、経営管理者がログイン後に店舗設定画面から1件以上作成する。新しい店舗の追加は経営管理者のみ、既存店舗の編集・閲覧は経営管理者（全店）／店長（自店のみ）。それ以外のロール（ホール・キッチン・バイト）は編集不可だが閲覧はテナント内であれば制限しない（2026-09-13改訂：店長の閲覧範囲を自店のみに限定。従来は編集不可のロールと同様に店長も全店閲覧可だった）。ユーザー登録画面での自己登録（FR-A03）は店舗を選ばせず、店舗への割り当てはログイン後のユーザー編集画面で行う（同画面は未実装）。 |
| 既存資産の流用 | 流用は「ユーザー登録・ログイン」と `company_code + email` 複合ユニーク制約、および Spring Boot ＋ React ＋ PostgreSQL の雛形のみ。その他は新規実装（着手前にコード棚卸しで最終確認）。 |

| モバイルオーダー | 卓マスタが持つQR識別子で卓を識別（FR-B02）。QRセッションは卓のクローズで失効（FR-F02）。いたずら対策のパラメータ等、残る実装詳細は該当機能の実装直前にスパイクで詰める。 |

## 4. 業務フロー（フェーズ1の主要シナリオ）

### 4.1 予約〜来店〜会計〜締め（標準フロー）

1. **予約**: 顧客がWeb予約フォームから申込、またはスタッフが電話予約を予約台帳へ入力。
2. **来店・着席**: スタッフが予約またはウォークインを卓に割り当て、卓を「利用中」にする（卓をオープン）。
3. **注文**:
   - スタッフがハンディ／タブレットで注文を入力する、または
   - 顧客が卓上QRを読み取り、自分のスマホの注文画面から注文を送信する（スタッフが受理）。
   - 確定した注文はキッチン（KDS／伝票）へ連携される。
4. **追加注文**: 3 を繰り返す。飲み放題・コースはラストオーダー時刻をシステムが通知。
5. **会計**: スタッフが対象卓の会計を作成。小計・税（軽減税率区分含む）・割引・クーポンを反映し、
   1つ以上の決済手段（現金／PayPay／クレジットカード／楽天ペイ）で精算。必要に応じて別会計・割り勘。
   レシート／領収書を発行。卓をクローズ。
6. **日次締め**: 閉店後、店長がレジ点検（現金実査）と日次締めを実行。当日の売上・客数・客単価・
   決済手段別内訳を含む売上日報が自動生成される。

### 4.2 例外・代替フロー（抜粋）

- **モバイルオーダーの品切れ**: 顧客が注文送信 → 対象品が売り切れ → スタッフが該当明細を却下し、
  顧客のスマホ画面に理由を表示。
- **注文の取消（提供前）**: キッチンに通す前・調理前の明細は、スタッフが理由を付して取消できる。
- **注文の取消（提供後）**: すでに調理・提供された品の取消は、キッチンと突き合わせて「実際に作ったか（＝廃棄ロスになるか）」「作り直すか」を確認したうえで行う。想定ケース：
  - オーダーテイクミス（違う品・数量を入力し、キッチンが作ってしまった）
  - 品質クレーム（異物、生焼け、冷めている、焼き加減違い等）→ 取消または無償、必要なら作り直しを再オーダー
  - 提供遅延で客が不要と申し出た
  - 誤配膳（別卓の品を出した／アレルギー対応漏れ）→ 該当卓の会計から除外し、正しい卓へ付け替え
  - 通した後に品切れが判明（営業中の材料切れ）
  - 客都合の気変わり（通した後・喫食前）
  提供後の取消・返金は理由の記録が必須で、監査ログ対象（FR-J01）。店舗設定により「要店長承認」にできる（FR-G10）。
- **取消と返金の境界**: 会計確定**前**は「取消（void）」で開いている会計から明細を削除する。会計確定**後**に判明した誤り（二重計上、値引き漏れ、コース内なのに単品計上等）は「返金（refund）」として記録し、元会計は削除せず返金イベントを追加する（FR-G10）。
- **キャンセル時の請求要否**: 客都合／店都合それぞれの「請求する／しない」の既定を店舗設定で持つ（FR-B08）。会計時にスタッフが個別に上書きできる。
- **オフライン**: ネットワーク断中もスタッフはタブレットで注文入力を継続でき、復旧後に同期（NFR）。
  モバイルオーダーはオフライン中は受け付けない（客側の再試行に委ねる）。
